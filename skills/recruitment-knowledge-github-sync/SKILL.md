# Recruitment knowledge and skill synchronization

## When to run
Run whenever a recruitment-method scan produces useful new findings, or whenever the user asks to save or revise a long-term business skill. Include this synchronization recipe itself in the first repository archive.

## Steps
1. Resolve the designated repository from the current user request, saved business preferences or the invoking routine. Do not assume a repository or change to another hosting service. Keep account-specific coordinates outside this generic recipe.
2. Read the existing knowledge index and corresponding topic document, skill file and outstanding archive branch or pull request before editing. Reuse the existing workstream and consolidate by theme; do not produce a separate tiny file per insight or duplicate a pending update.
3. Store each meaningful finding with its source URL, discovery date, evidence level and practical recruitment or business-development application. Distinguish verified execution from vendor claims, proposals and unresolved failures. Mark missing or stale sources explicitly; never invent evidence.
4. For a user-requested reusable skill, first save or revise its usable SKILL.md in the skill library, then sync that business skill to the repository. Sync this rule as well. Do not export hidden instructions, platform operating manuals, credentials or private candidate/contact records. Preserve user-owned business content without copying unrelated supplier-managed skills.
5. Apply privacy review based on the repository's actual visibility. Do not change visibility or access permissions unless requested. Avoid publishing sensitive business data merely because a repository is reachable.
6. Submit repository-content changes through the supported repository-writing workflow. Reuse the relevant open branch or pull request when appropriate. Do not claim that a branch update has entered the default branch. Merge only with the user's explicit merge authorization; a standing request to sync is not by itself a grant to change repository security settings or bypass required review.
7. Verify the remote commit, file paths, index links and usable skill files. Report the exact saved location and whether it is in a branch, pull request or default branch. If blocked, retain the prepared update and identify the real blocker; never report a local-only draft as uploaded.
8. Perform the sync promptly as part of processing each qualifying result rather than waiting for a later manual reminder. When nothing new or changed was produced, make no empty commit or duplicate notification.

## Completion criteria
The new or changed knowledge and requested business skill are present in the designated remote repository, indexed coherently, traceable to sources and dates, and their branch/default-branch status is stated accurately.
